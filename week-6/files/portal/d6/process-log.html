3. What worked

  1. Scout first, gated build second. The blank-shell scout produced a complete, runnable library with no client data in its head. The gated build then spent its time on differences from the scout, as the Week 4 lesson said.
  2. Running real data through synthetic-tested code. The scout's synthetic tests passed. Real data exposed two defects at once: the engine added the fund roll-up row to the company rows (Scope 1 would have read 23,899 t against 11,599 t) and the LP report printed company slugs and internal ids that the scout's name check missed. Both were fixed and each now has a check and a failing-case test.
  3. A clean re-run check that copies only the pinned inputs. It found two unpinned inputs before G2 and proves the leave-behind rebuilds byte for byte.
  4. Reading the output as the audience. Two separate Claude sessions given only the query pack found nine gaps and one real inconsistency. A reviewer reading as Sarah found the intensity figure did not recompute from the numbers printed beside it. A confirmation pass caught a misattribution (the executive assignment was the engagement owner's decision, not Northwood's).
  5. Questionnaire reads with quotes checked by script. Thirty answers were entered with a verbatim quote; the intake stops if a quote is not in the file.
  6. Decisions in the owner's words, as they were made. Every ruling went to the decision log the same turn, so packets could point to ids instead of re-explaining.
  7. Verifying frameworks against official text, and saying what was not read. The verification log found three errors in the scout's library (ESRS 2 governance numbering, the EDCI metric list, and the claim that UK SRS use is voluntary).

4. What did not work, or cost more than it should have

  1. The scout assumed an EU-facing LP base. Northwood's data room names no EU or UK LP, so the Tier 1 EU frameworks are library coverage, not what Northwood is asked for (D-6-39).
  2. Synthetic data hid the double count. A check on the headline figures (Q22) was added only after real data broke it. Put a fund-level roll-up row in every synthetic case, and a recompute check in the first version of any engine.
  3. Several sources could not be read the normal way. The IFRS S2 text is behind a login (AASB and UK SRS texts were used as the proxy). PDFs needed a workaround and each read needed the owner's yes. Plan for this in the next reference build.
  4. A gate step ran out of order. At G1 the sign-off was recorded after a check showed a stale-state false alarm. The sequence is now: regenerate the state, run the check, read the verdict, then record and freeze.
  5. Inputs and ids collided with the kit's rules late. Derived row ids read as decision ids, file locators needed full paths, two inputs were unpinned. Run lint after the first deliverable, not before the first packet.
  6. Week 4's "carbon" column was the wrong thing to show a board. It is the customer carbon-data line plus a small carbon-price piece. Before quoting a frozen column, recompute one example by hand.
  7. Peer benchmarks are thin. Public data supports a comparison for only two companies.
  8. The re-run needs a technical person. The nine steps are commands; the re-run note says who runs them and what Sarah reviews.
  9. A builder wrote into a frozen folder at close-out. The first v2 run of the dashboard builder wrote the query pack into the v1 folder, overwriting one frozen file. It was restored from the archived v1 builder and hash-checked against the freeze (J-072). Lesson: give every versioned output its own folder name, and hash-check the freezes after the first run of a changed builder.

5. Carry into the next engagement's reference build

  • Keep the library's shape (register, framework files with verification labels, applicability rules, playbook, method notes). Re-verify against official text at the start of each engagement.
  • Build the headline recompute and the name-leak scan before any real data. Put a fund roll-up row in every synthetic case.
  • Add the clean re-run check at the first deliverable.
  • Treat every PDF read and every file download as an approval to ask for at kickoff.
  • Ask the client at kickoff which LPs and frameworks actually request disclosure (DR6-11).
  • Ask for supplier spend by category and contractor headcount at kickoff (DR6-16), so Scope 3 can be estimated by category from the start.
  • Record the owner's rulings in his words in the same turn.
